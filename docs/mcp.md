# MCP-сервер «Уязвимости и хосты» (только чтение)

MCP-сервер даёт AI-клиентам (Claude Code, Cursor, Codex, Qwen, Hermes и любым другим клиентам с поддержкой MCP) read-only доступ к данным MP VM Client. Главный сценарий: **«на каких хостах сейчас есть уязвимость X?»** — сервер возвращает список хостов, а также сообщает, описано ли исправление в паспорте уязвимости MP VM.

Сервер ничего не меняет и ничего не запускает: нет исправления, сканирования, создания заявок и записи данных. Блок «исправление» — это только информация из паспорта.

## Как это устроено

```text
AI-клиент ──MCP (streamable HTTP, персональный Bearer-токен)──▶ https://<хост>/mcp
                                                                 │  тот же порт 8000, что и у приложения
                                                                 ▼
                              mpvm-client: путь /mcp ──токен проверяет приложение──▶ сессия владельца токена,
                                                       ограниченная правами чтения ──REST внутри процесса──▶ /api/… ──▶ PostgreSQL
```

- MCP встроен в сервис `mpvm-client` и отвечает на **том же порту 8000**, что и приложение, по отдельному пути `/mcp`. Reverse proxy перед приложением менять не нужно: достаточно, чтобы он пропускал `POST /mcp` и заголовок `Authorization`.
- Пока `MPVM_MCP_ENABLED` не равно `true`, путь не занят и приложение работает как раньше. Если конфигурация MCP неверна (например, некорректный путь), MCP не монтируется и пишет причину в лог, а приложение запускается как обычно.
- У каждого клиента свой **персональный токен**, выпущенный администратором в приложении: он привязан к владельцу, имеет области доступа и срок действия, хранится только в виде хеша и отзывается без перезапуска.
- Инструменты ходят в REST API приложения **внутри процесса** от имени владельца токена, но в сессии, ограниченной областями токена и правами только на чтение. Права, RBAC и аудит остаются в backend: даже ошибка в коде MCP или администратор в роли владельца не дадут записать данные, а клиент использует только `GET`.
- Данные берутся из **сохранённых карточек активов в локальной PostgreSQL**, а не из живого MP VM. Поэтому ответ нужно читать вместе с `last_seen`, `stale` и `data_source.coverage`.

## Подготовка

Токены выпускает администратор (право `security.mcp_tokens.manage`). Отдельная учётная запись для MCP и пароль в окружении больше не нужны.

1. Войдите администратором и выпустите токен. Секрет показывается **один раз** в ответе — сразу сохраните его в менеджере секретов клиента:

```bash
curl -c jar -X POST https://<хост>/api/auth/login -H 'Content-Type: application/json' \
  -d '{"username":"<админ>","password":"<пароль>","auth_type":"local"}'

curl -b jar -X POST https://<хост>/api/auth/mcp-tokens -H 'Content-Type: application/json' \
  -d '{"name":"claude-code-ivanov","scopes":["vulnerabilities:read"],"expires_in_days":90}'
```

   Поля запроса: `name` (имя клиента), `scopes` (области, ниже), `expires_in_days` (1–365, по умолчанию 90; бессрочных токенов нет), `owner_user_id` (владелец; по умолчанию вы), `ip_allowlist` (необязательный список адресов и сетей CIDR, с которых токен принимается).
2. Задайте переменные сервиса `mpvm-client` (в окружении оболочки или в локальном `.env`; файл с секретами не публикуйте). Для токенов достаточно `MPVM_MCP_ENABLED=true`:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MPVM_MCP_ENABLED` | `false` | `true` включает MCP на порту приложения. |
| `MPVM_MCP_PATH` | `/mcp` | Путь («ручка») MCP. Должен начинаться с `/`, нельзя занимать `/api/…` и `/static/…`. |
| `MPVM_MCP_ALLOWED_ORIGINS` | пусто | Разрешённые браузерные источники через запятую. Запрос с любым другим заголовком `Origin` получает `403`; клиенты, не являющиеся браузерами, его не шлют. |
| `MPVM_MCP_ALLOW_X_API_KEY` | `false` | Принимать токен ещё и в заголовке `X-API-Key`. По умолчанию выключено: токен принимается только как `Authorization: Bearer …`. |
| `MPVM_MCP_STALE_DAYS` | `14` | Через сколько дней без обновления карточки хост считается устаревшим (`stale`). |
| `MPVM_MCP_MAX_RESPONSE_CHARS` | `60000` | Предел размера ответа инструмента; длинные списки обрезаются с флагом `truncated`. |
| `MPVM_MCP_TIMEOUT_SECONDS` | `30` | Таймаут внутренних запросов к API. |

### Области доступа токена

Токен получает только права на чтение из выбранных областей, и только если они есть у его владельца. Права записи он не получает никогда, даже если владелец — администратор.

| Область | Что открывает | Инструменты |
| --- | --- | --- |
| `vulnerabilities:read` | `assets.read`, `asset_cards.read`, `passports.read` | поиск хостов и уязвимостей, карточки хостов, сводки, полнота данных |
| `remediation:read` | `remediation.read` | `list_remediation_cases`, `remediation_summary` |
| `operations:read` | `tasks.read`, `operations.read` | `list_scan_tasks`, `list_operations` |
| `risk:read` | `risk.read` | `risk_queue` |

Инструмент вне областей токена возвращает ошибку `PERMISSION_DENIED` от приложения.

### Управление токенами

Все запросы выполняются под администратором (сессия из шага 1); `GET /api/auth/mcp-tokens` возвращает токены и каталог областей без секретов.

```bash
# замена токена: новый выдаётся сразу, старый работает ещё grace_hours часов (0 — отозвать сразу)
curl -b jar -X POST https://<хост>/api/auth/mcp-tokens/<id>/rotate -H 'Content-Type: application/json' -d '{"grace_hours":24}'

# отзыв: все сессии токена закрываются немедленно
curl -b jar -X POST https://<хост>/api/auth/mcp-tokens/<id>/revoke
```

У одного владельца не больше 20 действующих токенов. Отключение владельца, смена его пароля, отзыв и истечение срока закрывают сессии токена сразу.

## Запуск

```bash
docker compose up -d --build mpvm-client
```

В логах приложения должна появиться строка `MCP is served at /mcp on the application port`. Проверка (токен нужен, без него будет `401` от MCP, а не `405` от приложения):

```bash
curl -i -X POST https://<хост>/mcp -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -H "Authorization: Bearer $MPVM_MCP_TOKEN" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Ответ `405 Method Not Allowed` означает, что запрос дошёл до приложения, но MCP выключен или не смонтирован: проверьте `MPVM_MCP_ENABLED` и лог запуска.

### Reverse proxy

Прокси должен передавать `POST` на `/mcp` в приложение без изменений и не терять заголовок `Authorization`. Если перед приложением стоит nginx со своим `location /`, отдельное правило не нужно. Для `location /mcp` достаточно:

```nginx
location /mcp {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
    proxy_http_version 1.1;
    proxy_read_timeout 300s;
}
```

Нужна другая «ручка» (например, прокси разрешает только `/vulnsearch/mcp`) — задайте `MPVM_MCP_PATH=/vulnsearch/mcp`. Путь с завершающим `/` (`/mcp/`) принимается без перенаправления.

## Подключение клиентов

Любой клиент, который умеет streamable HTTP, подключается по URL `https://<хост>/mcp` с заголовком `Authorization: Bearer <персональный токен>` (если клиент умеет только произвольные заголовки, включите `MPVM_MCP_ALLOW_X_API_KEY=true` и передавайте `X-API-Key: <токен>`). Сервер работает в stateless-режиме с JSON-ответами и согласует версии протокола `2025-03-26`, `2025-06-18` и `2025-11-25`. Других путей (`/api/mcp`, `/mcp/v1`, `/messages`) нет: клиенту не нужно их угадывать.

Примеры (синтаксис конфигурации зависит от версии клиента — сверяйтесь с его документацией):

```bash
# Claude Code
claude mcp add --transport http mpvm https://<хост>/mcp --header "Authorization: Bearer $MPVM_MCP_TOKEN"
```

```json
{
  "mcpServers": {
    "mpvm": {
      "url": "https://<хост>/mcp",
      "headers": { "Authorization": "Bearer <токен>" }
    }
  }
}
```

Последний формат используют Cursor (`.cursor/mcp.json`) и ряд других клиентов; в Qwen Code вместо `url` используется поле `httpUrl`. Для Codex и Hermes задайте тот же URL и заголовок в их конфигурации MCP-серверов.

## Инструменты

Все инструменты помечены `readOnlyHint: true`.

| Инструмент | Что делает |
| --- | --- |
| `find_hosts_by_vulnerability` | **Главный.** По CVE, id или названию возвращает хосты с уязвимостью, найденные селекторы, `fix`, число устаревших хостов и блок `data_source`. Фильтры: `severity`, `source` (`os`/`software`/`docker`), `host_q`, `limit`, `offset`; `detail` (`brief` по умолчанию или `full`); `include_coverage` добавляет глобальную полноту данных, но это медленно (на большой БД минуты), поэтому по умолчанию выключено. |
| `get_vulnerability_fix_info` | Можно ли исправить уязвимость по паспорту MP VM (только информация). |
| `search_vulnerabilities` | Поиск уязвимостей: число затронутых хостов, фильтры по критичности, источнику, наличию исправления. |
| `list_host_vulnerabilities` | Уязвимости одного хоста с признаком исправления. |
| `find_hosts`, `get_host` | Поиск хостов и сохранённая карточка хоста. |
| `vulnerability_summary` | Сводка по критичности, топ уязвимостей и хостов, полнота и свежесть данных. Запрос тяжёлый: на большой БД может занимать минуты. |
| `trending_vulnerabilities` | Трендовые уязвимости MP VM. |
| `list_remediation_cases`, `remediation_summary` | Отслеживание исправлений: статус, исполнитель, SLA, просрочка. Только чтение. |
| `data_freshness` | Покрытие данных: хосты без карточки, устаревшие, усечённые, с ошибкой. |
| `list_scan_tasks`, `list_operations` | Задачи сканирования и фоновые операции с прогрессом. |
| `risk_queue` | Хосты по приоритету риска. |

### Как читать ответ `find_hosts_by_vulnerability`

- `match`: `exact` — найдено точное совпадение CVE/id/названия; `partial` — точного нет, показаны частичные совпадения (поиск в API идёт по подстроке, поэтому `CVE-2024-1` без этой проверки захватил бы `CVE-2024-10`); `none` — ничего не найдено.
- Один CVE в приложении может иметь несколько селекторов (ОС, ПО, Docker, разные id паспортов). Сервер объединяет хосты по `asset_id`, а в каждом хосте перечисляет `selectors`.
- `fix.status`:
  - `available` — паспорт описывает исправление (`fix.how_to_fix`);
  - `not_described` — паспорт загружен, но описания исправления в нём нет;
  - `unknown` — паспорта нет или его детали ещё не загружены, ответить нельзя. В приложении флаг `has_fix=false` смешивает эти случаи, поэтому здесь они разделены; `fix.reason` объясняет причину.
- `hosts[].stale` — карточка хоста старше `MPVM_MCP_STALE_DAYS`; такой хост мог уже быть исправлен или удалён. `data_source.hosts_oldest_last_seen` и `hosts_freshest_last_seen` — самая старая и самая свежая карточка среди найденных хостов. Глобальная полнота (`data_source.coverage`: `complete`, `freshest_at`, `oldest_at`, `truncated_groups`) приходит только с `include_coverage=true`; если за 20 секунд её получить не удалось, будет `coverage: null` и пояснение.
- `detail=brief` (по умолчанию): `hosts` — компактные строки-массивы в порядке `host_columns` (`asset_id`, `name`, `ip`, `os`, `severity`, `last_seen` (дата), `age_days`, `stale`, `src` — источники `os`/`software`/`docker`, `component` — уязвимые ПО/объекты и docker-образ (до трёх, до 120 символов), `case` — статус заявки на устранение). Блок `fix` короче: текст исправления до 600 символов (полный даёт `get_vulnerability_fix_info`), без пустых полей. `detail=full` отдаёт объект на каждый хост со всеми полями и примерно в 4–6 раз больше по размеру.
- Повторный и постраничный (`offset`) запрос с теми же `query` и фильтрами в течение 2 минут берётся из кэша сервера без обращения к БД; одинаковые одновременные запросы выполняются один раз. После этого срока данные запрашиваются заново.
- `hosts_by_severity` — сколько найденных хостов на каждом уровне критичности (по всем страницам, а не только по возвращённой). Пустые поля в строках хостов опущены; если селектор один, `selectors` не выводится.
- `hosts[].remediation` — заявки на устранение для этой пары «хост — уязвимость», если они есть.
- `truncated: true` — результат неполон (слишком много совпадений или ответ обрезан по размеру); сузьте запрос или листайте `offset`.

## Ограничения и безопасность

- Данные не «живые»: они настолько свежи, насколько свежа последняя сборка карточек. Актуализация выполняется приложением (сканирование, обновление карточек), а не MCP.
- Секрет токена показывается один раз и хранится только как SHA-256 хеш; в аудит и логи он не попадает. Передавайте токен только по HTTPS (TLS на прокси) и храните как секрет. Потеряли — отзовите и выпустите новый.
- Токен не может писать: его сессия ограничена областями токена и правами чтения, а владелец с правами записи этого не меняет. Токеном нельзя ни выпускать другие токены, ни читать пользователей и аудит.
- Токен действует не дольше срока (до 365 дней). Просроченный, отозванный токен или токен отключённого владельца отвергается, а его сессии закрываются немедленно.
- Все отказы выглядят одинаково (`401`), чтобы не подсказывать, что именно неверно. После нескольких неудачных попыток с одного адреса приложение отвечает `429` с `Retry-After`. Адрес берётся из соединения: за прокси он будет адресом прокси, поэтому `ip_allowlist` имеет смысл при прямом подключении или когда прокси передаёт настоящий адрес клиента.
- Аудит приложения (`/api/auth/audit`) хранит выпуск, замену и отзыв токенов (`mcp_token_created`, `mcp_token_rotated`, `mcp_token_revoked`), отказы входа с причиной (`mcp_auth`), открытие сессии (`mcp_session`) и каждый вызов инструмента (`mcp_tool_call`: инструмент, длительность, результат). Все события несут имя токена и его владельца; аргументы запросов не записываются.
- Кэши ответов MCP раздельны для каждого токена: ответ, полученный с правами одного токена, не отдаётся другому.
- Ответы инструментов (имена, IP и ПО хостов) попадают в AI-клиент и дальше к его провайдеру модели. Подключайте только те клиенты, которым разрешено видеть эти данные.
- Заголовок `Origin` проверяется: запросы из браузера принимаются только из `MPVM_MCP_ALLOWED_ORIGINS`.
- Сессия токена в приложении живёт до часа; MCP открывает её по мере необходимости и один раз пробует заново при `401`.

## Проверка

Тесты запускаются только в Docker (см. [testing.md](testing.md)):

```bash
docker compose -p mpvm-ui-tests -f compose.test.yml up -d test-postgres
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm tests python -m pytest -p no:cacheprovider tests/mcp_server tests/integration/test_mcp_server_db.py
```

- `tests/mcp_server/` — модульные тесты (подменённый API): выбор селекторов, три статуса исправления, устаревшие хосты, пагинация, повторное открытие сессии, проверка токена (в том числе отказ без токена, `Origin`, `X-API-Key`), раздельные сессии и кэши токенов, аудит вызовов, схема инструментов и `readOnlyHint`, а также встроенный режим на порту приложения (путь, `/mcp/` без редиректа, SPA и `/api` не затронуты, неверная конфигурация не ломает запуск).
- `tests/integration/test_mcp_server_db.py` — сквозные тесты на реальной PostgreSQL и реальном RBAC: список хостов, `fix.status`, и то, что токен даже у владельца-администратора получает `403` на создание заявки, запуск сканирования и удаление карточки.
- `tests/integration/test_mcp_tokens_db.py` — токены на реальной PostgreSQL: выпуск и хранение хеша, права администратора, отказы (просрочен, отозван, владелец отключён, чужой адрес), лимит попыток, потолок прав сессии даже у администратора, немедленное закрытие сессий, замена с периодом совместимости, аудит и сквозной вызов через `/mcp`.
