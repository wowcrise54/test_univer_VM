# MCP-сервер «Уязвимости и хосты» (только чтение)

MCP-сервер даёт AI-клиентам (Claude Code, Cursor, Codex, Hermes и любым другим клиентам с поддержкой MCP) read-only доступ к данным MP VM Client. Главный сценарий: **«на каких хостах сейчас есть уязвимость X?»** — сервер возвращает список хостов, а также сообщает, описано ли исправление в паспорте уязвимости MP VM.

Сервер ничего не меняет и ничего не запускает: нет исправления, сканирования, создания заявок и записи данных. Блок «исправление» — это только информация из паспорта.

## Как это устроено

```text
AI-клиент ──MCP (streamable HTTP + Bearer-токен | stdio)──▶ mpvm-mcp ──REST, роль viewer──▶ mpvm-client ──▶ PostgreSQL
```

- `mcp_server/` — отдельный Python-пакет и отдельный контейнер (`Dockerfile.mcp`). Он не импортирует `app.*` и не подключается к БД.
- Сервер — тонкий клиент REST API приложения под выделенной локальной учётной записью с ролью `viewer`. Права, RBAC и аудит остаются в backend: даже ошибка в коде MCP-сервера не даст записать данные, а клиент использует только `GET` (единственное исключение — вход для получения cookie-сессии).
- Данные берутся из **сохранённых карточек активов в локальной PostgreSQL**, а не из живого MP VM. Поэтому ответ нужно читать вместе с `last_seen`, `stale` и `data_source.coverage`.

## Подготовка

1. Под администратором создайте локального пользователя (раздел управления доступом приложения или `POST /api/auth/users`) с ролью **`viewer`**, например `mcp-viewer`; пароль — не короче 12 символов. Не выдавайте роль `operator` или `admin`: при старте сервер пишет предупреждение в лог, если у учётной записи есть права на изменения.
2. Сгенерируйте токен доступа к самому MCP-серверу, например `openssl rand -hex 32`.
3. Задайте переменные (в окружении оболочки или в локальном `.env`; файл с секретами не публикуйте):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MPVM_MCP_USERNAME`, `MPVM_MCP_PASSWORD` | — (обязательны) | Учётная запись `viewer` в приложении. |
| `MPVM_MCP_AUTH_TOKEN` | — | Токен клиентов MCP (`Authorization: Bearer …` или `X-API-Key`). Обязателен, если сервер слушает не loopback-адрес. |
| `MPVM_MCP_API_URL` | `http://mpvm-client:8000` | Адрес REST API приложения. |
| `MPVM_MCP_TRANSPORT` | `streamable-http` | `streamable-http` или `stdio`. |
| `MPVM_MCP_HOST`, `MPVM_MCP_PORT` | `127.0.0.1` (в образе `0.0.0.0`), `8765` | Адрес и порт HTTP-сервера. |
| `MPVM_MCP_BIND` | `127.0.0.1` | Только для Compose: на каком адресе хоста публиковать порт. |
| `MPVM_MCP_STALE_DAYS` | `14` | Через сколько дней без обновления карточки хост считается устаревшим (`stale`). |
| `MPVM_MCP_VERIFY_TLS` | `true` | Проверка TLS при обращении к `MPVM_MCP_API_URL` по HTTPS. |
| `MPVM_MCP_TIMEOUT_SECONDS` | `30` | Таймаут запросов к API. |
| `MPVM_MCP_MAX_RESPONSE_CHARS` | `60000` | Предел размера ответа инструмента; длинные списки обрезаются с флагом `truncated`. |

Если пароли лежат в общем `.env`, учтите, что Compose передаёт этот файл и контейнеру `mpvm-client` (`env_file`); чтобы не делить секреты между контейнерами, задавайте `MPVM_MCP_*` в окружении оболочки.

## Запуск

Сервис описан в `docker-compose.yml` с профилем `mcp` и по умолчанию не запускается, поэтому основной стек не меняется:

```bash
docker compose --profile mcp up -d --build mpvm-mcp
```

Порт публикуется только на `127.0.0.1:8765`, эндпоинт — `http://127.0.0.1:8765/mcp`, проверка готовности без токена — `http://127.0.0.1:8765/healthz`. Образ собирается из публичного PyPI (`PIP_INDEX_URL` можно переопределить аргументом сборки).

Если сервер открывается за пределы хоста (`MPVM_MCP_BIND=0.0.0.0`), ставьте перед ним TLS-прокси: токен передаётся открытым текстом.

## Подключение клиентов

Любой клиент, который умеет streamable HTTP, подключается по URL `http://127.0.0.1:8765/mcp` с заголовком `Authorization: Bearer <токен>` (если клиент умеет только произвольные заголовки — `X-API-Key: <токен>`). Сервер работает в stateless-режиме с JSON-ответами и согласует версии протокола `2025-03-26`, `2025-06-18` и `2025-11-25`.

Примеры (синтаксис конфигурации зависит от версии клиента — сверяйтесь с его документацией):

```bash
# Claude Code
claude mcp add --transport http mpvm http://127.0.0.1:8765/mcp --header "Authorization: Bearer $MPVM_MCP_AUTH_TOKEN"
```

```json
{
  "mcpServers": {
    "mpvm": {
      "url": "http://127.0.0.1:8765/mcp",
      "headers": { "Authorization": "Bearer <токен>" }
    }
  }
}
```

Последний формат используют Cursor (`.cursor/mcp.json`) и ряд других клиентов. Для Codex и Hermes задайте тот же URL и заголовок в их конфигурации MCP-серверов.

Режим **stdio** нужен клиентам, которые сами запускают процесс. Токен в этом режиме не используется, а доступ ограничен правами того, кто запускает контейнер:

```bash
docker run -i --rm --network <проект>_default -e MPVM_MCP_TRANSPORT=stdio -e MPVM_MCP_USERNAME -e MPVM_MCP_PASSWORD \
  -e MPVM_MCP_API_URL=http://mpvm-client:8000 <образ mpvm-mcp> python -m mcp_server
```

## Инструменты

Все инструменты помечены `readOnlyHint: true`.

| Инструмент | Что делает |
| --- | --- |
| `find_hosts_by_vulnerability` | **Главный.** По CVE, id или названию возвращает хосты с уязвимостью, найденные селекторы, `fix`, число устаревших хостов и блок `data_source`. Фильтры: `severity`, `source` (`os`/`software`/`docker`), `host_q`, `limit`, `offset`. |
| `get_vulnerability_fix_info` | Можно ли исправить уязвимость по паспорту MP VM (только информация). |
| `search_vulnerabilities` | Поиск уязвимостей: число затронутых хостов, фильтры по критичности, источнику, наличию исправления. |
| `list_host_vulnerabilities` | Уязвимости одного хоста с признаком исправления. |
| `find_hosts`, `get_host` | Поиск хостов и сохранённая карточка хоста. |
| `vulnerability_summary` | Сводка по критичности, топ уязвимостей и хостов, полнота и свежесть данных. |
| `trending_vulnerabilities` | Трендовые уязвимости MP VM. |
| `list_remediation_cases`, `remediation_summary` | Отслеживание исправлений: статус, исполнитель, SLA, просрочка. Только чтение. |
| `data_freshness` | Покрытие данных: хосты без карточки, устаревшие, усечённые, с ошибкой. |
| `list_scan_tasks`, `list_operations` | Задачи сканирования и фоновые операции с прогрессом. |
| `risk_queue` | Хосты по приоритету риска. |

### Как читать ответ `find_hosts_by_vulnerability`

- `match`: `exact` — найдено точное совпадение CVE/id/названия; `partial` — точного нет, показаны частичные совпадения (поиск в API идёт по подстроке, поэтому `CVE-2024-1` без этой проверки захватил бы `CVE-2024-10`); `none` — ничего не найдено.
- Один CVE в приложении может иметь несколько селекторов (ОС, ПО, Docker, разные id паспортов). Сервер объединяет хосты по `asset_id`, а в каждом хосте перечисляет `selectors`.
- `fix.status`:
  - `available` — паспорт описывает исправление (`fix.how_to_fix`);
  - `not_described` — паспорт загружен, но описания исправления в нём нет;
  - `unknown` — паспорта нет или его детали ещё не загружены, ответить нельзя. В приложении флаг `has_fix=false` смешивает эти случаи, поэтому здесь они разделены; `fix.reason` объясняет причину.
- `hosts[].stale` — карточка хоста старше `MPVM_MCP_STALE_DAYS`; такой хост мог уже быть исправлен или удалён. `data_source.coverage` — глобальная полнота и свежесть локальных данных (`complete`, `freshest_at`, `oldest_at`, `truncated_groups`).
- `hosts[].remediation` — заявки на устранение для этой пары «хост — уязвимость», если они есть.
- `truncated: true` — результат неполон (слишком много совпадений или ответ обрезан по размеру); сузьте запрос или листайте `offset`.

## Ограничения и безопасность

- Данные не «живые»: они настолько свежи, насколько свежа последняя сборка карточек. Актуализация выполняется приложением (сканирование, обновление карточек), а не MCP-сервером.
- Все запросы выполняются под одной учётной записью; в аудите приложения они видны под её именем и `User-Agent: mpvm-mcp/…`.
- Ответы инструментов (имена, IP и ПО хостов) попадают в AI-клиент и дальше к его провайдеру модели. Подключайте только те клиенты, которым разрешено видеть эти данные.
- После нескольких неудачных входов приложение блокирует учётную запись на время; сервер повторяет вход не чаще раза в 30 секунд и не зацикливается на неверном пароле.
- Сессия приложения живёт 12 часов; при `401` сервер один раз входит заново.

## Проверка

Тесты запускаются только в Docker (см. [testing.md](testing.md)):

```bash
docker compose -p mpvm-ui-tests -f compose.test.yml up -d test-postgres
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm tests python -m pytest -p no:cacheprovider tests/mcp_server tests/integration/test_mcp_server_db.py
```

- `tests/mcp_server/` — модульные тесты (подменённый API): выбор селекторов, три статуса исправления, устаревшие хосты, пагинация, повторный вход, Bearer-проверка, схема инструментов и `readOnlyHint`.
- `tests/integration/test_mcp_server_db.py` — сквозные тесты на реальной PostgreSQL и реальном RBAC: список хостов, `fix.status`, и то, что учётная запись `viewer` получает `403` на создание заявки, запуск сканирования и удаление карточки.
