# MCP-сервер «Уязвимости и хосты» (только чтение)

MCP-сервер даёт AI-клиентам (Claude Code, Cursor, Codex, Qwen, Hermes и любым другим клиентам с поддержкой MCP) read-only доступ к данным MP VM Client. Главный сценарий: **«на каких хостах сейчас есть уязвимость X?»** — сервер возвращает список хостов, а также сообщает, описано ли исправление в паспорте уязвимости MP VM.

Сервер ничего не меняет и ничего не запускает: нет исправления, сканирования, создания заявок и записи данных. Блок «исправление» — это только информация из паспорта.

## Как это устроено

```text
AI-клиент ──MCP (streamable HTTP, Bearer-токен)──▶ https://<хост>/mcp
                                                     │  тот же порт 8000, что и у приложения
                                                     ▼
                                          mpvm-client: путь /mcp ──REST внутри процесса, роль viewer──▶ /api/… ──▶ PostgreSQL
```

- MCP встроен в сервис `mpvm-client` и отвечает на **том же порту 8000**, что и приложение, по отдельному пути `/mcp`. Reverse proxy перед приложением менять не нужно: достаточно, чтобы он пропускал `POST /mcp` и заголовок `Authorization`.
- Пока `MPVM_MCP_ENABLED` не равно `true`, путь не занят и приложение работает как раньше. Если конфигурация MCP неверна (нет токена, учётной записи или некорректный путь), MCP не монтируется и пишет причину в лог, а приложение запускается как обычно.
- Инструменты ходят в REST API приложения **внутри процесса** под выделенной локальной учётной записью `viewer`. Права, RBAC и аудит остаются в backend: даже ошибка в коде MCP не даст записать данные, а клиент использует только `GET` (единственное исключение — вход для получения cookie-сессии).
- Данные берутся из **сохранённых карточек активов в локальной PostgreSQL**, а не из живого MP VM. Поэтому ответ нужно читать вместе с `last_seen`, `stale` и `data_source.coverage`.

## Подготовка

1. Под администратором создайте локального пользователя с ролью **`viewer`**, например `mcp-user` (раздел **«Пользователи»** → **«Новый пользователь»** или `POST /api/auth/users`); пароль — не короче 12 символов. Не выдавайте роль `operator` или `admin`: при первом входе сервер пишет предупреждение в лог, если у учётной записи есть права на изменения. Учётная запись должна быть локальной (не LDAP).
2. Сгенерируйте токен доступа к самому MCP, например `openssl rand -hex 32`.
3. Задайте переменные для сервиса `mpvm-client` (в окружении оболочки или в локальном `.env`; файл с секретами не публикуйте):

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `MPVM_MCP_ENABLED` | `false` | `true` включает MCP на порту приложения. |
| `MPVM_MCP_USERNAME`, `MPVM_MCP_PASSWORD` | — (обязательны) | Учётная запись `viewer` в приложении. |
| `MPVM_MCP_AUTH_TOKEN` | — (обязателен) | Токен клиентов MCP (`Authorization: Bearer …` или `X-API-Key`). |
| `MPVM_MCP_PATH` | `/mcp` | Путь («ручка») MCP. Должен начинаться с `/`, нельзя занимать `/api/…` и `/static/…`. |
| `MPVM_MCP_STALE_DAYS` | `14` | Через сколько дней без обновления карточки хост считается устаревшим (`stale`). |
| `MPVM_MCP_MAX_RESPONSE_CHARS` | `60000` | Предел размера ответа инструмента; длинные списки обрезаются с флагом `truncated`. |
| `MPVM_MCP_TIMEOUT_SECONDS` | `30` | Таймаут внутренних запросов к API. |

## Запуск

```bash
docker compose up -d --build mpvm-client
```

В логах приложения должна появиться строка `MCP is served at /mcp on the application port`. Проверка (токен нужен, без него будет `401` от MCP, а не `405` от приложения):

```bash
curl -i -X POST https://<хост>/mcp -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -H "Authorization: Bearer $MPVM_MCP_AUTH_TOKEN" -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

Ответ `405 Method Not Allowed` означает, что запрос дошёл до приложения, но MCP выключен или не смонтирован: проверьте `MPVM_MCP_ENABLED` и лог запуска.

### Reverse proxy

Прокси должен передавать `POST` на `/mcp` в приложение без изменений и не терять заголовок `Authorization`. Если перед приложением стоит nginx со своим `location /`, отдельное правило не нужно. Для `location /mcp` достаточно:

```nginx
location /mcp {
    proxy_pass http://127.0.0.1:8000;
    proxy_set_header Host $host;
    proxy_set_header Authorization $http_authorization;
    proxy_http_version 1.1;
    proxy_read_timeout 300s;
}
```

Нужна другая «ручка» (например, прокси разрешает только `/vulnsearch/mcp`) — задайте `MPVM_MCP_PATH=/vulnsearch/mcp`. Путь с завершающим `/` (`/mcp/`) принимается без перенаправления.

## Подключение клиентов

Любой клиент, который умеет streamable HTTP, подключается по URL `https://<хост>/mcp` с заголовком `Authorization: Bearer <токен>` (если клиент умеет только произвольные заголовки — `X-API-Key: <токен>`). Сервер работает в stateless-режиме с JSON-ответами и согласует версии протокола `2025-03-26`, `2025-06-18` и `2025-11-25`. Других путей (`/api/mcp`, `/mcp/v1`, `/messages`) нет: клиенту не нужно их угадывать.

Примеры (синтаксис конфигурации зависит от версии клиента — сверяйтесь с его документацией):

```bash
# Claude Code
claude mcp add --transport http mpvm https://<хост>/mcp --header "Authorization: Bearer $MPVM_MCP_AUTH_TOKEN"
```

```json
{
  "mcpServers": {
    "mpvm": {
      "url": "https://<хост>/mcp",
      "headers": { "Authorization": "Bearer <токен>" }
    }
  }
}
```

Последний формат используют Cursor (`.cursor/mcp.json`) и ряд других клиентов; в Qwen Code вместо `url` используется поле `httpUrl`. Для Codex и Hermes задайте тот же URL и заголовок в их конфигурации MCP-серверов.

## Инструменты

Все инструменты помечены `readOnlyHint: true`.

| Инструмент | Что делает |
| --- | --- |
| `find_hosts_by_vulnerability` | **Главный.** По CVE, id или названию возвращает хосты с уязвимостью, найденные селекторы, `fix`, число устаревших хостов и блок `data_source`. Фильтры: `severity`, `source` (`os`/`software`/`docker`), `host_q`, `limit`, `offset`. |
| `get_vulnerability_fix_info` | Можно ли исправить уязвимость по паспорту MP VM (только информация). |
| `search_vulnerabilities` | Поиск уязвимостей: число затронутых хостов, фильтры по критичности, источнику, наличию исправления. |
| `list_host_vulnerabilities` | Уязвимости одного хоста с признаком исправления. |
| `find_hosts`, `get_host` | Поиск хостов и сохранённая карточка хоста. |
| `vulnerability_summary` | Сводка по критичности, топ уязвимостей и хостов, полнота и свежесть данных. |
| `trending_vulnerabilities` | Трендовые уязвимости MP VM. |
| `list_remediation_cases`, `remediation_summary` | Отслеживание исправлений: статус, исполнитель, SLA, просрочка. Только чтение. |
| `data_freshness` | Покрытие данных: хосты без карточки, устаревшие, усечённые, с ошибкой. |
| `list_scan_tasks`, `list_operations` | Задачи сканирования и фоновые операции с прогрессом. |
| `risk_queue` | Хосты по приоритету риска. |

### Как читать ответ `find_hosts_by_vulnerability`

- `match`: `exact` — найдено точное совпадение CVE/id/названия; `partial` — точного нет, показаны частичные совпадения (поиск в API идёт по подстроке, поэтому `CVE-2024-1` без этой проверки захватил бы `CVE-2024-10`); `none` — ничего не найдено.
- Один CVE в приложении может иметь несколько селекторов (ОС, ПО, Docker, разные id паспортов). Сервер объединяет хосты по `asset_id`, а в каждом хосте перечисляет `selectors`.
- `fix.status`:
  - `available` — паспорт описывает исправление (`fix.how_to_fix`);
  - `not_described` — паспорт загружен, но описания исправления в нём нет;
  - `unknown` — паспорта нет или его детали ещё не загружены, ответить нельзя. В приложении флаг `has_fix=false` смешивает эти случаи, поэтому здесь они разделены; `fix.reason` объясняет причину.
- `hosts[].stale` — карточка хоста старше `MPVM_MCP_STALE_DAYS`; такой хост мог уже быть исправлен или удалён. `data_source.coverage` — глобальная полнота и свежесть локальных данных (`complete`, `freshest_at`, `oldest_at`, `truncated_groups`).
- `hosts[].remediation` — заявки на устранение для этой пары «хост — уязвимость», если они есть.
- `truncated: true` — результат неполон (слишком много совпадений или ответ обрезан по размеру); сузьте запрос или листайте `offset`.

## Ограничения и безопасность

- Данные не «живые»: они настолько свежи, насколько свежа последняя сборка карточек. Актуализация выполняется приложением (сканирование, обновление карточек), а не MCP.
- MCP делит порт с приложением, поэтому единственной защитой пути `/mcp` служит токен: передавайте его только по HTTPS (TLS на прокси) и храните как секрет. Остальные пути приложения защищены, как и раньше, сессией.
- Все запросы выполняются под одной учётной записью; в аудите приложения они видны под её именем.
- Ответы инструментов (имена, IP и ПО хостов) попадают в AI-клиент и дальше к его провайдеру модели. Подключайте только те клиенты, которым разрешено видеть эти данные.
- После нескольких неудачных входов приложение блокирует вход на время; MCP повторяет вход не чаще раза в 30 секунд и не зацикливается на неверном пароле.
- Сессия приложения живёт 12 часов; при `401` MCP один раз входит заново.
- Смена токена или пароля учётной записи требует перезапуска `mpvm-client`.

## Проверка

Тесты запускаются только в Docker (см. [testing.md](testing.md)):

```bash
docker compose -p mpvm-ui-tests -f compose.test.yml up -d test-postgres
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm tests python -m pytest -p no:cacheprovider tests/mcp_server tests/integration/test_mcp_server_db.py
```

- `tests/mcp_server/` — модульные тесты (подменённый API): выбор селекторов, три статуса исправления, устаревшие хосты, пагинация, повторный вход, Bearer-проверка, схема инструментов и `readOnlyHint`, а также встроенный режим на порту приложения (токен, путь, `/mcp/` без редиректа, SPA и `/api` не затронуты, неверная конфигурация не ломает запуск).
- `tests/integration/test_mcp_server_db.py` — сквозные тесты на реальной PostgreSQL и реальном RBAC: список хостов, `fix.status`, и то, что учётная запись `viewer` получает `403` на создание заявки, запуск сканирования и удаление карточки.
