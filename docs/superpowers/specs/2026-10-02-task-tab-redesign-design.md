# Переработка вкладки задач

## Цель

Сделать вкладку задач MP VM рабочим пространством: группировать задачи по общим папкам, быстро просматривать выбранную задачу, открывать историю запусков и редактировать параметры в отдельной форме. Список должен содержать только поиск задач без фильтров по статусу, профилю или другим полям.

## Принятые решения

- Сохраняется текущая вкладка `/tasks` и существующие API создания, изменения, запуска, остановки и удаления задач.
- Задачи и результаты остаются в MP VM. Локальная PostgreSQL хранит только папки, их имена и связи между папками и ID задач MP VM.
- Папки общие для пользователей приложения. Одна задача находится не более чем в одной папке; задачи без назначения доступны в разделе «Без группы».
- Удаление папки удаляет ее связи и возвращает задачи в «Без группы». Удаление задачи удаляет ее локальную связь с папкой после успешного завершения существующего сценария удаления.
- Поиск выполняется по названию и ID задач. В разделе «Все задачи» он охватывает все задачи; при выбранной папке или «Без группы» поиск ограничен этим разделом. Других фильтров нет.
- Существующие RBAC-разрешения сохраняются: просмотр задач, папок и деталей требует `tasks.read`; управление задачами и папками — `tasks.manage`; запуск и остановка — `tasks.execute`. Backend проверяет разрешения независимо от интерфейса.
- Запись изменений папок и назначения задач включает пользователя и время в существующий аудит.

## Список задач

Вкладка разделяется на три области:

1. Слева — дерево «Все задачи», созданные папки и «Без группы». Пользователь с `tasks.manage` может создавать, переименовывать и удалять папки.
2. По центру — поисковая строка и таблица задач. Таблица показывает статус, название, цели, профиль, сведения о сборе данных, дату создания, коллекторы, учетную запись, последний запуск и следующий запуск, если MP VM отдает эти данные.
3. Справа — краткие сведения о выбранной задаче: дата создания, статус, последний запуск, включенные и исключенные цели, профиль, коллекторы и параметры расписания.

Одинарное нажатие строки только выбирает задачу и обновляет правую панель. Оно не загружает результаты и не открывает форму редактирования. Панель действий позволяет открыть детали, изменить, копировать, переместить в папку, проверить, запустить, остановить или удалить задачу. Каждое действие доступно только при соответствующем разрешении и состоянии задачи. Перемещение в папку также доступно из меню действий строки. Выбор папки, текст поиска и выбранная задача сохраняются при возврате из деталей или формы.

Таблица и папки остаются адаптивными: на узкой ширине панели переходят в последовательное представление, а таблица сохраняет возможность горизонтальной прокрутки.

## Подробности задачи

Двойное нажатие строки открывает подробности внутри вкладки `/tasks`. Для доступности отдельная кнопка «Открыть подробности» открывает тот же экран; Enter/Space на строке выбирают задачу, а не открывают ее.

Экран повторяет структуру второго примера:

- слева — описание задачи и ее параметры;
- в центре — история запусков;
- справа — результаты выбранного запуска по целям/подзадачам.

Выбор запуска подгружает его задания из MP VM. В таблице показываются статус и итоговый статус, начало и окончание, длительность, коллектор, цели и профиль. Для precheck дополнительно показываются результаты проверок соединения по транспортам и ошибки. Состояния загрузки, пустой истории, ошибок и повтора запроса отображаются в соответствующей панели. Кнопка возврата сохраняет состояние списка.

## Создание и изменение задачи

Новая задача, изменение и копирование открывают отдельное представление формы на вкладке `/tasks`. Оно использует карточки с прокруткой и закрепленную нижнюю панель действий «Сохранить», «Сохранить и запустить» и «Отмена».

Форма сохраняет текущие поля и черновики. Карточки группируют:

- название и описание;
- параметры сбора: инфраструктуру, профиль, коллекторы, учетную запись, цели и исключения, FQDN, HostDiscovery и precheck;
- расписание запуска;
- запрещенное время сканирования;
- расширенные таймауты, интервалы опроса и проверки готовности.

Расписание включает переключатель, часовой пояс, начало/окончание действия и условные поля типа расписания. Реализуются типы v3 API: `Daily`, `Periodic`, `RepeatableDaily`, `Weekly`, `Fortnightly`, `Monthly` и `CronScheduler`; отображаются только параметры, необходимые выбранному типу. Запрещенное время включает переключатель и список периодов; каждый период задает дни недели, часовой пояс и либо весь день, либо начало и окончание. Изменение формы сериализуется в `triggerParameters` и `deniedScanSettings` API MP VM, а при редактировании оба блока восстанавливаются из `task.payload`. Отключенные настройки сохраняют существующее поведение по умолчанию. Схема полей основана на документации MP VM для endpoint-а `/api/scanning/v3/scanner_tasks`: [руководство по API](https://help.ptsecurity.com/ru-RU/projects/siem/8.0/help/8592978955).

При копировании поля выбранной задачи и ее расписание переносятся в новую форму без исходного ID; удаленная задача или копия не меняют назначение исходной задачи в папке.

## Локальное хранение папок и API

Добавляется Alembic-миграция с таблицами папок задач и назначений. Идентификатор задачи хранится как локальная строка без внешнего ключа на MP VM. Идентификатор папки — UUID с внешним ключом на таблицу папок; уникальность имени папки обеспечивается без учета регистра. Каждая операция выполняется параметризованным SQL и транзакционно.

Добавляются endpoint-ы:

- `GET /api/scanner-task-folders` — папки и ID назначенных задач;
- `POST /api/scanner-task-folders` — создать папку;
- `PATCH /api/scanner-task-folders/{folder_id}` — переименовать папку;
- `DELETE /api/scanner-task-folders/{folder_id}` — удалить папку и ее назначения;
- `PUT /api/scanner-task-folders/assignments` — назначить выбранные задачи папке или снять назначение, если `folder_id` равен `null`.

Все операции управления папками требуют `tasks.manage`; чтение требует `tasks.read`. Пустые имена и имена-дубликаты возвращают структурированную ошибку; отсутствующая папка возвращает 404. Папки не меняют данные в MP VM.

## API истории и совместимость

Добавляются read-only endpoint-ы:

- `GET /api/scanner-tasks/{task_id}/runs` — страница истории запусков с offset/limit;
- `GET /api/scanner-tasks/{task_id}/runs/{run_id}/jobs` — задания выбранного запуска.

Оба endpoint-а требуют `tasks.read`. Перед чтением заданий backend проверяет, что `run_id` принадлежит `task_id`. Для запросов к MP VM используются существующие методы клиента и безопасная обработка ошибок/недоступности соединения.

`GET /api/scanner-tasks/{task_id}/results` продолжает возвращать результаты последнего запуска в прежнем формате. Форматы CRUD и действия существующих API задач также остаются совместимыми. Поля расписания и запрещенных периодов добавляются в структурированную модель запроса и в существующий mapper payload; произвольные данные клиента не должны попадать в MP VM в обход валидации.

## Ошибки и безопасность

- Ошибка загрузки папок или истории не скрывает уже загруженный список и дает повторить соответствующий запрос.
- Если изменение папки или назначения не сохранено на сервере, интерфейс показывает ошибку и не оставляет ложное оптимистичное состояние.
- Неподключенный MP VM отображается как отдельное состояние подробностей; локальная структура папок остается доступной.
- Рендер экрана и автоматические тесты не запускают реальные удаленные операции.
- Фактический запуск задачи идет по существующему пути с `tasks.execute` и ключом идемпотентности.
- Новые SQL-запросы размещаются в репозитории, бизнес-правила — в сервисе, миграция — в `migrations/versions/`; HTTP-роутер остается тонким.

## Проверки

Backend и PostgreSQL проверяются внутри Docker Compose проекта с отдельной тестовой PostgreSQL. Проверяются миграция, создание/переименование/удаление папок, уникальность имен без учета регистра, назначения, аудит и RBAC. Удаленная интеграция тестируется подмененным MP VM клиентом без реального запуска задачи.

Payload-тесты проверяют выключенные настройки по умолчанию и сериализацию каждого поддерживаемого типа расписания и запрещенных периодов. Тесты API проверяют чтение страницы запусков, выбранных заданий, принадлежность run к задаче и сохранение формата старого `/results`.

Frontend-тесты проверяют поиск и области групп, одинарный выбор без сетевого запроса, двойное открытие деталей, переключение запусков, действия по ролям, editor draft, расписание, запрещенные периоды и состояния ошибок. Frontend-тесты, lint, форматирование и сборка запускаются только в Docker.

## Критерии приемки

- Список содержит поиск задач и папки; дополнительные фильтры отсутствуют.
- Одинарное нажатие только выбирает задачу; двойное открывает подробности с историей запусков и результатами выбранного запуска.
- Инспектор справа отображает основные параметры выбранной задачи.
- Папки и назначения общие для пользователей, переживают перезапуск приложения и управляются через backend с RBAC.
- Создание, изменение и копирование используют новую карточную форму и сохраняют все действующие поля.
- Настройки расписания и запрещенного времени корректно формируют соответствующие поля API MP VM для создания и изменения.
- Существующие контракты CRUD, запусков и `/results` продолжают работать.
- Макет остается пригодным на узких экранах, а действия ограничены server-side RBAC.
