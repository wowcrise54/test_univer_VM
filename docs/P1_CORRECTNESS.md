# Исправления корректности — 2026-10-01

## Свидетельства эксплуатации

Миграция `20261001_0025` пересоздаёт материализованные generated columns и пересчитывает существующие паспорта. `exploitation_evidence` имеет три значения: `true`, `false`, `null` (сведений недостаточно). Локальная модель риска теперь `local-risk-v2`; дополнительные пять баллов даёт только `true`.

Поддерживается явно наблюдавшееся верхнеуровневое поле `exploit` с JSON boolean в `raw_detail_json`, `metrics_json`, `raw_record_json`. Текст, имена других полей, вложенные значения и повреждённый JSON не подтверждают эксплуатацию. Если явные значения источников противоречат друг другу, результат неизвестен. Новые vendor-поля требуют согласованного контракта и примеров реальных обезличенных payload.

Очередь возвращает `exploitation_evidence_source` с названием источника и поля, а также `exploitation_evidence_updated_at`: время обновления detail либо последнего наблюдения паспорта. Это дата актуальности источника, а не дата самой эксплуатации; исторические данные не позволяют восстановить дату события.

## Каталог разрешений

`app/api/permissions.py` содержит фиксированный каталог `(HTTP method, route template) → permission`. Для нового защищённого endpoint нужна явная запись. Middleware проверяет реально выбранный маршрут, включая скрытые маршруты; неизвестные чтения и записи запрещены всем ролям. Неподдерживаемый метод существующего маршрута также возвращает 403.

Отдельно зарегистрированный HEAD требует собственной политики. HEAD и GET одного общего обработчика используют его явную GET-политику. Публичные `/api/auth/login`, `/api/auth/bootstrap-status`, `/api/health`, `/api/live`, `/api/ready` и особые authenticated `/api/auth/me`, `/api/auth/logout` сохраняют прежние исключения.

## Готовность и восстановление

* `/api/live`: HTTP 200, `{"ok":true}` — процесс обслуживает запросы.
* `/api/ready`: HTTP 200 только после соединения с PostgreSQL, совпадения Alembic heads и завершения recovery; иначе 503. Возвращает `ready`, `database_ready`, `schema_current`, `recovery_complete`, при необходимости безопасную причину. Доступность MP VM сообщается отдельно и не блокирует локальную готовность.
* Старый `/api/health` сохраняет HTTP 200, `ok:true` и состав ответа; `database_ready` теперь учитывает весь recovery. Для проверки готовности следует использовать `/api/ready`.

Контейнер приложения владеет recovery-координатором. Он повторяет незавершённые startup-этапы под lock и проверяет БД каждые пять секунд, включая сценарий позднего появления PostgreSQL без запросов к health. Успешные этапы выполняются один раз за lifecycle; scheduler запускается последним. Ошибка внутри snapshot, backfill или resume не считается успешным завершением этапа. Shutdown останавливает monitor до scheduler и worker runner. Это координация одного процесса; multi-instance эксплуатация не добавлена.

## Версии контекста и кампаний

`PATCH /api/assets/context` принимает optional `expected_versions: {asset_id: version}`; отсутствие контекста соответствует версии 0. Для переданных ожиданий backend блокирует родительские активы в стабильном порядке и сравнивает версии. Конфликт возвращает 409 `VERSION_CONFLICT`; изменения всего batch и его аудит откатываются. CSV импорт использует snapshot версий и сообщает конфликт в ошибках конкретной строки.

`PATCH /api/remediation/campaigns/{campaign_id}` принимает optional `expected_version` и сравнивает её под блокировкой записи. Устаревшее ожидание возвращает 409 без изменения данных и аудита. Даже PATCH без изменения полей проверяет переданное ожидание.

UI всегда отправляет версии снимка, с которого началось редактирование. После конфликта черновик сохраняется, повторное сохранение блокируется до явного перечитывания. Старые API-клиенты без ожиданий сохраняют прежнюю семантику; защиты от устаревшей записи у них нет. Сделать ожидания обязательными можно отдельным изменением API после перехода внешних клиентов.

## Проверки и применение

Регрессионные тесты проверяют отрицательные/неизвестные свидетельства, конфликт источников, миграцию старых записей, реальные PostgreSQL-конфликты создания/обновления, rollback аудита, UI snapshot и перечитывание, неизвестные и скрытые GET/HEAD, поздний startup БД, временные ошибки отдельных recovery-этапов и отсутствие второго scheduler. Миграции проверяются upgrade/downgrade/re-upgrade в отдельных scratch databases.

Все проверки выполняются в Docker с отдельной tmpfs PostgreSQL 16. Браузерные e2e используют mock API. Рабочая БД, MP VM и рабочий стек при проверках не изменяются; миграция в рабочем окружении ещё не применена. Изменение требует обычного развёртывания текущих исходников и Alembic upgrade до `20261001_0025`.

Финальная проверка: backend — 1264 passed; frontend — 283 passed; браузерные e2e — 13 passed. Ruff, mypy, ESLint, Prettier format check, Vite build и оба coverage gates прошли. Python line coverage 81,55% при baseline 81,10%; frontend 69,00% при baseline 68,60%; critical branch coverage 90,5% при пороге 90,3%. Независимое ревью завершилось без существенных открытых замечаний. Рабочее применение миграции и взаимодействие с реальным MP VM этим прогоном не проверялись.
