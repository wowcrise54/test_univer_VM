# Тестирование в Docker

Все тесты, измерение покрытия, lint, type-check и сборка выполняются в Docker. Backend использует отдельную PostgreSQL 16 из `compose.test.yml`: у неё нет опубликованных портов, данные хранятся в tmpfs. Рабочий стек и его volumes в проверках не участвуют.

## Полный прогон

Команды выполняются последовательно из корня репозитория. Не запускайте несколько backend-наборов одновременно против одной тестовой БД: fixtures очищают её состояние перед каждым интеграционным тестом.

```powershell
docker compose -p mpvm-ui-tests -f compose.test.yml up -d test-postgres
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm --build tests python -m pytest -p no:cacheprovider --cov=app --cov-branch --cov-report=json:output/coverage-python.json
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm --build --no-deps frontend-tests
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm --build --no-deps e2e
```

`Dockerfile.test` устанавливает backend test-зависимости; текущие исходники монтируются только для чтения. `Dockerfile.frontend.test` устанавливает frontend-зависимости через `npm ci` по lockfile и включает текущие исходники при сборке. Поэтому для повторной проверки изменённого frontend используйте `--build`.

`frontend-tests` запускает Vitest с покрытием, ESLint, Prettier и Vite build. `e2e` использует системный Chromium внутри образа и запускает приложение в браузере через Playwright. В этих контейнерах внешняя сеть отключена; браузерные API-ответы подменены fixtures, реальные операции MP VM не запускаются.

Отчёты сохраняются в `output/coverage-python.json`, `output/coverage-js/coverage-summary.json`, `output/playwright/report/`; неудачные e2e оставляют traces и screenshots в `output/playwright/results/`. Сборка frontend остаётся внутри временного test-контейнера.

## Python quality gate и пороги покрытия

После получения обоих отчётов:

```powershell
docker compose -p mpvm-ui-tests -f compose.test.yml run --rm --no-deps tests sh -c 'ruff check app/core app/api app/automations app/domain app/mpvm app/repositories app/services app/factory.py tests/test_architecture.py tests/test_automations.py && mypy app/core app/api app/automations app/domain app/mpvm app/repositories app/services app/factory.py && python scripts/check_coverage_thresholds.py --report output/coverage-python.json && python scripts/check_coverage_ratchet.py --python output/coverage-python.json --frontend output/coverage-js/coverage-summary.json'
```

`.coverage-ratchet.json` защищает общее покрытие строк отдельно для Python и frontend. `.coverage-thresholds.json` задаёт пороги ветвей для критической и остальных групп backend, а `module_floors` — отдельные требования строк/ветвей для выбранных модулей. Отсутствующий в отчёте модуль тоже приводит к отказу gate.

Vitest учитывает все `src/**/*.js` и `src/**/*.jsx`, включая не импортированные тестами исходники; исключены только сами `src/test/`. Для Python измеряются строки и ветви всего `app`. Проценты строк и ветвей считаются отдельно: объединённый `percent_covered` в pytest-cov JSON не является процентом строк.

## Что проверяют расширенные наборы

- Диагностика: архивы, фильтрация по операции/trace/job, повреждённые файлы, redaction, HTTP/SQL telemetry, CLI, commit/rollback PostgreSQL.
- MP VM: HTTP-конверты, пагинация, пустые коллекции, CSV/PDQL, сканеры, динамические группы, завершение/таймаут/остановка, сохранение успешных precheck-целей.
- HTTP-сервисы: фильтры, ограничения доступа, ошибки, expected_version, идемпотентность, cancel/retry.
- Автоматизации: валидация определений, условия и сохранённые результаты шагов, восстановление, отмена, ограничения повторов, ошибки scheduler/webhook. Повторный запуск с тем же ключом возвращает исходный run даже после публикации новой версии; изменение параметров запроса с тем же ключом даёт HTTP 409 без создания второго run. Если run удалён между загрузкой определения и началом шага, обработчик шага не вызывается, а связанная операция завершается как `cancelled` с `finished_at` и прогрессом 100%.
- VM workflow: дедупликация workers, восстановление child-операций, частичный прогресс, временно отсутствующие операции, ошибки запуска, отмена и сохранение конечного статуса при запоздалой ошибке.
- PostgreSQL: группы активов, контекст и приоритет риска, кампании, атомарность, версии и аудит. Remediation проверяет согласованное применение фильтров, общий счётчик на пустой странице, ручные сроки SLA, конфликт версий, комментарии, явное подтверждение возобновления исключений и повторное открытие устранённой уязвимости.
- Безопасность: LDAP-фильтры/OU/группы, сетевые отказы, пароли, лимит входа, пользователи и роли, последний администратор, отзыв сессий, настоящее HTTP/RBAC взаимодействие.
- Каталог паспортов: прогресс, результаты и аргументы фоновых detail-задач, ошибки загрузки/постановки в очередь, ограничение длины сообщений, отмена до запроса и перед отправкой detail-задач. PostgreSQL проверяет единственное активное обновление, его приоритет над более новой завершённой операцией, восстановление после перезапуска и сохранение конечного статуса при запоздалом прогрессе или отмене.
- Compliance и attention/search: реальные SQL-запросы, приоритет даты завершённого сканирования над датой карточки, свежесть на границе 30 дней, выборка активов и scope, дедупликация по источнику, сортировка и общий счётчик на пустой странице. Проверяются права каждой категории поиска/attention, просроченные SLA, retry-действия, причины неполного покрытия, курсоры, исключение удалённых задач и resolved-кейсов, буквальный поиск `%`, `_`, обратной косой черты и SQL-спецсимволов.
- Пресеты ПО: поиск по любой части названия без учёта регистра во всех шести пресетах, включая `git` → `GitLab CE`; фильтры версии и Windows сохраняются. 16 PostgreSQL-тестов проверяют реальные запросы, группировку установок, спецсимволы и точный выбор продукта/версии для списка активов. UI-тест проверяет передачу частичного запроса и полного названия найденного продукта при открытии активов.
- Frontend: маршруты и доступ, загрузка/ошибки/повтор, React Query и polling, черновики задач, уведомления, compliance-отчёты, автоматизации, устранение, SLA, кампании и импорт CSV.
- E2E: desktop/tablet/mobile, операции и диагностика, отдельные действия выбора задачи/результатов/создания, применение выборки уязвимостей, workflow и scan-confirmed устранение.

100% строк и ветвей закреплены порогами для 24 backend-модулей: диагностика, config, OAuth, LDAP, сервисы/репозитории риска и групп активов, сервис диагностики операций, выделенные API-роутеры, репозиторий автоматизаций и VM-workflow, domain/repository/service compliance, репозиторий attention/search, репозиторий и сервис обновления каталога паспортов. У модулей без ветвей gate считает покрытие ветвей равным 100%. Ещё для сервиса автоматизаций и репозитория remediation установлены повышенные минимальные пороги строк и ветвей. UsersPage и ComplianceDashboard также имеют 100% строк и ветвей; App, useAppData и RemediationPage покрыты на 100% строк.

Полный проект пока не имеет 100% покрытия. Основные оставшиеся пробелы — большие переходные фасады `app/main.py`, `app/db.py`, `src/panels.jsx` и отдельные workflow/UI ветви. Интеграционные тесты PostgreSQL проверяют версии runbook, восстановление и отмену запусков, повторы webhook, SLA, истечение исключений, сверку уязвимостей, freshness/truncation и классификацию инвентаря; они также закрепляют найденное сохранение общего числа при пустой странице пагинации.

Последний полный backend-прогон: 1219 тестов и 24 подтеста; покрытие строк 81,24% (9747/11998), ветвей 70,56% (2605/3692). Расширение compliance, attention/search и каталога паспортов добавило 47 тестов: 10 проверок границ worker/domain и 37 PostgreSQL-сценариев; затем исправление поиска ПО добавило 16 PostgreSQL-тестов и один UI-тест. Шесть модулей compliance, attention/search и каталога паспортов достигли 100% строк и ветвей. Репозиторий автоматизаций и VM workflow сохраняют 100% строк и ветвей, сервис автоматизаций — 99,70%/99,22%, репозиторий remediation — 98,91%/96,51%. Минимальные пороги повышены до 81,1% строк Python, 90,3% ветвей критической группы и 65,1% остальных ветвей; для новых полностью покрытых модулей установлен отдельный порог 100%. Последний полный frontend-прогон: 279 тестов, 68,61% строк и 57,86% ветвей; ESLint, проверка форматирования и сборка также прошли. E2E сохраняет результат предыдущего прогона — 13 сценариев; после изменения поиска ПО повторно не запускался. Поиск проверяется на тестовых карточках и отдельной PostgreSQL, реальные операции MP VM не запускаются.
