# Первый этап: тесты и безопасность backend

## Исходное состояние

Сохранённый `output/coverage-python.json` создан 12 июля 2026 года: 57,42% строк, без измерения ветвей. Это исторический показатель. Старые пороги составляли 53% строк, 36% ветвей критичных модулей и 48,5% ветвей остальных модулей.

В рабочем дереве до начала этапа уже были изменения в `app/repositories/vm_workflows.py`, `app/services/vm_workflows.py` и соответствующих тестах. Они сохранены без перезаписи.

## Подтверждённые находки и изменения

| Риск | Наблюдение | Изменение |
| --- | --- | --- |
| Высокий: повторная мутация MP VM | `build_retry_adapter()` автоматически повторял `POST`, `PUT` и `DELETE` после ошибок ответа. Повтор мог создать или удалить объект дважды. | Автоматический повтор ограничен `GET`, `HEAD`, `OPTIONS`; для мутаций используются сценарии приложения с сохранённым состоянием и ключами идемпотентности. |
| Средний: утечка данных внешнего API | Текст ошибок MP VM включал тело ответа, в том числе поля `access_token` и `client_secret`. | Структурированные ответы проходят редактирование чувствительных полей; текстовые ответы не отражаются в ошибке. |
| Средний: неработающий порог покрытия ветвей | CI запускал pytest без `--cov-branch`, а проверка считала отчёт без данных по ветвям как 100%. | CI собирает покрытие ветвей; проверка отклоняет отчёт без измерения ветвей. |
| Средний: уязвимая зависимость | `pip-audit` выявил [CVE-2026-58203](https://github.com/pydantic/pydantic-settings/security/advisories/GHSA-4xgf-cpjx-pc3j) в `pydantic-settings==2.12.0`. Уязвимый `NestedSecretsSettingsSource` приложением не используется, но версия закреплена с известной проблемой. | Закреплена исправленная версия `2.14.2`, тестовый образ пересобран; `pip-audit` добавлен в CI. |
| Средний: неверное сравнение покрытия строк | После включения `--cov-branch` скрипт общего порога сравнивал суммарное покрытие строк и ветвей с порогом строк. | Скрипт использует `percent_statements_covered`; регрессионный тест проверяет формат отчёта с ветвями. |

Ручная проверка затронула карту маршрутов и RBAC, динамический SQL и сортировку, настройки TLS, журналирование, HTTP-клиент и состояния workflow. Первичный `pip-audit` по закреплённым зависимостям нашёл одну уязвимость, указанную выше. Повторный аудит после обновления не получил результата из-за ошибки DNS при обращении из контейнера к PyPI и OSV; отсутствие других уязвимостей этим не подтверждено.

## Незавершённая верификация

Полный backend suite в Docker: 513 тестов и 24 подтеста прошли. Ruff прошёл, mypy не нашёл ошибок в 42 файлах. Покрытие строк — 66,13% при новом пороге 65%; ветви критичных модулей — 52,8% при пороге 52%, остальных — 49,8% при пороге 49%. Тесты работали с отдельной PostgreSQL 16 из `compose.test.yml` на временном хранилище. Повторный `pip-audit` остаётся непроверенным из-за DNS контейнера; CI теперь запускает его при доступной сети.
