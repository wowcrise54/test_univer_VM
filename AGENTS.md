# MP VM Client — инструкции агенту

## Главный принцип

Понимай намерение пользователя из контекста и **доводи задачу до законченного, проверяемого результата**.

Фразы вроде «можешь ли ты», «хочу», «помоги», «почини», «добавь» считай поручением к действию.

Не останавливайся после первого устранимого сбоя. Не спрашивай подтверждение на очевидные промежуточные шаги. Если данных достаточно — принимай разумное решение и продолжай.

Перед изменениями проверяй `git status` и текущий diff. Не сбрасывай, не перезаписывай и не присваивай себе чужие или незавершённые изменения.

Пользователю отвечай по-русски. Файлы сохраняй в UTF-8.

Не создавай коммиты, не публикуй изменения и не перезапускай рабочий стек без соответствующего поручения.

## Проект

MP VM Client состоит из React/Vite frontend, FastAPI backend и локальной PostgreSQL. С MP VM приложение работает через API; локальная PostgreSQL не является БД MP VM.

Основные границы:

* `app/api/` — HTTP и DTO;
* `app/services/` — бизнес-сценарии;
* `app/repositories/` — SQL и доступ к данным;
* `app/mpvm/`, `app/mpvm_client.py` — интеграция с MP VM;
* `app/automations/` — runbook-автоматизации;
* `src/features/` — frontend-сценарии;
* `src/shared/` — общие компоненты;
* `src/api/` — API-клиент;
* `migrations/` — Alembic.

Новый SQL размещай в repositories, бизнес-логику — в services, а не в HTTP handlers.

`app/main.py`, `app/db.py`, `app/mpvm_client.py` и `src/panels.jsx` — переходные фасады. Не раздувай их новыми крупными сценариями.

README и `docs/ARCHITECTURE.md` используй как ориентир, но при расхождении доверяй текущему коду.

Для известного файла или локальной правки отдельный запрос к Graphify не обязателен.

Не перестраивай граф без прямого запроса.

## Критичные правила

Сохраняй существующие API-контракты, маршруты UI, RBAC `admin/operator/viewer`, доступность и адаптивность.

Авторизация должна обеспечиваться backend, а не только скрытием элементов UI.

Для scan/postprocess/remediation и фоновых workflow сохраняй идемпотентность, отмену, прогресс, ограничение параллелизма и восстановление после перезапуска.

Не удаляй активы в MP VM до успешного локального сохранения. Не запускай реальные удалённые операции ради тестов.

Сохраняй аудит, `expected_version`, проверки свежести и полноты данных.

Для PostgreSQL используй параметризованный SQL, корректные типы, транзакции и Alembic-миграции. Не проверяй PostgreSQL-логику через SQLite.

Не выводи `.env`, токены, пароли, cookies и другие секреты.

## Проверки — только Docker

Все backend/frontend/integration/e2e тесты, lint, type-check, coverage и сборку запускай **только внутри Docker**.

Не используй для проверок Windows-host `.venv`, host Node/Python или локальную установку зависимостей.

Перед запуском:

1. определи актуальный Compose-файл и сервисы;
2. проверь, что окружение содержит текущие исходники и test-зависимости;
3. при необходимости используй отдельный временный test-контейнер.

Production-контейнер не считай тестовым окружением автоматически.

Интеграционные тесты и миграции запускай только против отдельной тестовой PostgreSQL. Не удаляй рабочие volumes и не используй `docker compose down -v`.

Не меняй major-версию существующей PostgreSQL без отдельного поручения.

Если Docker недоступен — не подменяй проверки запуском на хосте. Укажи, что именно осталось непроверенным.

Используй актуальные команды проекта из `quality.yml`, `package.json` и `pyproject.toml`. Типичные проверки:

* backend: `python -m pytest`;
* frontend: `npm test`;
* lint/format: `npm run lint`, `npm run format:check`;
* build: `npm run build`;
* e2e: `npm run test:e2e`.

Не ослабляй тесты и coverage-пороги ради прохождения.

## Завершение задачи

После изменений:

1. проверь diff;
2. запусти релевантные проверки в Docker;
3. исправь найденные ошибки;
4. повтори проверки;
5. только после этого считай задачу выполненной.

Не объявляй баг исправленным только по чтению кода.

В финале кратко укажи:

* что изменено;
* какие проверки выполнены;
* результат;
* что осталось непроверенным и почему.

**Не оставляй очевидный следующий шаг пользователю, если можешь выполнить его сам.**
